# Service, DNA and combat architecture (steps 1–6)

One repository, one Cloudflare Worker, one static client origin. The user declared step 5 complete and authorized step 6 only on 10 October 2026. Step 5 was user-reported deployed at the existing workers.dev origin. The local step 6 tree adds real automatic combat and three-round results; publication is not authorized. Cards/cabinet, audio/signals and final acceptance remain later stages. No custom-domain routes or paid dependencies are added.

## Stable infrastructure

| Binding | Class | Responsibility |
| --- | --- | --- |
| `ROOMS` | `LaboratoryRoom` | Room state, seats, admission, phases, deadlines, reconnect and hibernating WebSockets |
| `MATCHMAKING` | `MatchmakingPool` | One coordinator per coarse region: FIFO tickets, ready checks, allocation journal and vacancy offers |
| `GUEST_LEASES` | `GuestLease` | Server-issued browser identities and atomic claims across queues and rooms |

Class identities, bindings and declarative SQLite exports in `wrangler.json` remain unchanged. Objects are named `room:<code-or-public-id>`, `pool:<region>` and `guest:<uuid>`. The `control:private-entry` room instance bounds anonymous entry attempts and allocates private codes. A guest control object, `control:guest-identities`, retains replay-safe issuance mappings.

Rooms persist an explicit schema-5 JSON record in SQLite. Schema-4 migration preserves DNA/credentials/deadlines/receipts but adds no retroactive rival or battle: existing active attempts retain their frozen pre-combat boundary. A private host can explicitly start a new combat session there; public guests can leave and choose Quick Play. Fresh ordinary rounds enable combat. Stored combat versions and event/result boundaries are validated without rerolling. See STEP-6-PLAN.md for compatibility details. Migration from schema 2 first adds `publicState: null`; schema-2/3 records then gain mechanics fields while preserving seats, credentials, claims, score, receipts and deadlines. A legacy briefing gets a fresh attempt and deals at its existing experiment boundary. Legacy active experiments/releases/battles retain service-only behavior without retroactive doses or a new deadline; their next new attempt can use DNA. Unknown schemas fail closed. Schema-2 public contracts remain supported for binding-only legacy fixtures; actual matchmaking allocations always carry a region and enforce guest leases. Additional SQL tables retain action receipts, rate windows and creation mappings. Pool state includes ready checks and allocation journals. Guest identity records include hashed access tokens, private HMAC secrets and the current fenced claim.

Events reload SQLite state. Per-object promise queues serialize asynchronous operations. Room state, action receipts and alarms commit before acknowledgment; allocation journals commit before cross-object calls. A persisted room notification outbox publishes only vacancy context to its pool, **after releasing the room event queue**, avoiding a room/coordinator deadlock. Monotonic notification sequence numbers reject stale offers. Pending notifications retry by alarm, including after reactivation.

| Route | Method | Contract |

| `/api/queue/:region/socket` | GET upgrade | Protocols `mm-queue-v5, guest.<uuid>, token.<accessToken>`; replies with `mm-queue-v5` only |
| `/api/rooms/private` | POST | `{ operationId, alias, presentation }`; collision-checked six-character private code and host seat |
| `/api/rooms/:id/join` | POST | Private `{ operationId, alias, role: player \| display }` |
| `/api/rooms/:id/admit` | POST | Public `{ operationId, reservationId, admissionToken }`; issued identity and lease required |
| `/api/rooms/:id/snapshot` | GET | Seat bearer token; public state plus only its owner's controller |
| `/api/rooms/:id/socket` | GET upgrade | `mm-v5, token.<reconnectToken>`; replies with `mm-v5` only |
| `/api/rooms/:id/display` | POST | Participant bearer token plus `{ operationId }`; separate display credential |

Queue HTTP operations use `X-Guest-Id` and `Authorization: Bearer <accessToken>`. Private create/join includes `X-Guest-Id` and `X-Guest-Token` when the browser already has an issued identity; that guest cannot also occupy another queue or room. Legacy/private-only invitation guests still have independent anonymous seat identities. These credentials are browser identities, not verified people: separate browser profiles can deliberately create independent identities.

Tokens never appear in invitation URLs, query strings, public room projections or other guests' queue projections. JSON bodies are streamed with a 4 KiB limit; room messages are exact validated JSON at most 2 KiB. Queue sockets synchronize owner status and accept only `sync` plus automatic `ping`/`pong`; queue intentions use authenticated HTTP. Cross-origin browser requests fail, with the existing local Vite exception.

Room entry keys and action IDs are secret/random UUIDs. Entry fingerprints detect changed retries; reconnect tokens are HMAC-derived and compared as SHA-256 hashes. A room supports eight players, four displays, 128 historical admissions/reservations and 1,024 mutation receipts per seat. Entry limits remain 5 creations and 30 entry attempts per IP per minute, 10 seat connections per minute, 30 room actions per 10 seconds and 4 display grants per issuer per minute. Queue HTTP/sync operations are limited to 30 per guest per 10 seconds. Pools retain at most 1,000 tickets and 2,000 notification histories; the issuer retains at most 4,096 issuance mappings, and each guest at most 1,024 cancellation tombstones. Shared-IP groups share limits.

## Queue allocation and guest fencing

Three pools: Americas, Europe/Africa, Asia/Pacific. The client probes their response times and chooses the fastest responding pool, with manual override. This measures requests to the service; it does not pin Cloudflare execution to a continent. Queueing requires an explicit choice. Fresh tickets never consume replacement offers.

Four waiting guests trigger a ten-second ready check. FIFO additions fill that check to six without extending its deadline. With two or three waiting guests, the oldest thirty-second wait triggers the check; fewer than two remain waiting. After sixty seconds the UI offers another pool or a private invitation without changing pools automatically. At the deadline, two confirmed fresh guests suffice; nonresponders become inactive and must explicitly resume. Confirmed guests in a failed check keep their original queue priority.

The coordinator journals an allocation UUID, member reservation UUIDs and expiry before contacting a room. Room allocation is idempotent. Each guest authority atomically transfers the exact queue claim to the exact room/reservation. Partial failures revoke reservations and return eligible guests to their original priority. Reactivation retries the same journal rather than creating another room. Room admission and connection independently verify the lease. A cancellation tombstone prevents a delayed transfer or admission from reviving a cancelled ticket; subsequent queue consent uses a new ticket. Once the participant connects, cancellation uses the room Leave intent.

Claims have a two-minute technical expiry and renew while the queue/seat is live, at intervals of roughly forty-five seconds. Conditional release checks both holder and nonce so old callbacks cannot release a newer claim. Unused admission grants expire after ten seconds (and never after a replacement window); the room releases pending claims, and owner status becomes inactive for explicit resumption. Stale queue connections become inactive after sixty seconds. Ticket/allocation history expires after two hours; guest credentials and cancellation history have a twenty-four-hour idle lifetime. Alarm maintenance does not extend an idle identity forever.

## Public room progression

Public rooms have no player host. Two admitted, connected players start briefing automatically; remaining fresh grants may join during briefing before the experiment player count locks. Private rooms retain host-controlled starts, mid-round waiting seats and display invitations. A second room socket requires explicit replacement; hibernating attachments and authoritative deadlines preserve reconnection behavior.

The authoritative timeline is `lobby → briefing (8s) → experiment (75s) → release (5s) → battle (KO or ≤30s) → autopsy`, repeated for three fresh creatures, then session results. A session chooses three distinct rivals before briefing. Private hosts advance completed rounds and explicitly replay with 2+ connected players; `battleId`/`sessionId` fences and SQL receipts reject stale or duplicated progression. Waiting seats acquire a fresh budget at the next experiment boundary.

At release, the immutable specimen feeds the server-only pure combat producer. One private seed, complete event timeline and result are persisted together with a deadline before broadcast. The alarm commits exactly one result and 100/50/0 team points. Public snapshots expose the same timeline/start time and health/anatomy frames, never the seed or unrevealed result. Numeric creature stats and trait details are revealed at autopsy. Previously completed results and cumulative observed commendations remain in the bounded session record. Playback seeks by synchronized time without a server frame loop or animation backlog.

The binding-only `finishPublicBattle(sessionId, completionId, outcome)` remains for legacy orchestration/migration fixtures. For a real generated battle, only the stored ID/outcome after its deadline qualifies; production completion is internal. Browsers cannot call this method or supply outcomes. The combat runtime suite verifies actual automatic completion rather than inventing results.

Public autopsy lasts twenty-five seconds; all active players choosing Next Round may advance after ten seconds. Pending reservations prevent early advance until admitted or expired. Explicit Fill Existing Laboratory tickets get the round, team score, approximate remaining length and vacancy/recovery reason before Ready. Room capacity and phase are checked again when reserving and admitting. A result window that advances while a fill ready check is pending may reject that allocation and return its confirmed guest with original priority. Replacements never inject into an active experiment, inherit a departed identity or receive earlier personal credit. New eligible experiment boundaries reset doses and privately deal fresh specimens.

Disconnect grace remains fifteen seconds. Fewer than two eligible players suspends an unfinished experiment for thirty seconds; failed reconnection abandons only that attempt and opens a sixty-second recovery lobby. Two confirmed participants retry the same round. Completed score remains. Timeout presents explicit queue/exit choices and never queues the guest automatically. Already-started battles finish and commit recoverable results despite disconnects; they never rewind.

Session end opens thirty seconds for explicit replay opt-in. Two opting in start a new session UUID with reset score; nonparticipants leave that session. Fewer than two preserve the results and choose queue or exit. Find New Laboratory acknowledges leaving before entering a fresh queue. The inactivity prompt/seat-expiry hook is implemented for initialized per-round participation counters; accepted injections and switch actions initialize/update those counters. Mechanics-unavailable service rounds do not label every player inactive.

Room state, secrets and receipts expire after two hours without participant activity or twenty-four hours total. Hibernating heartbeat responses do not manufacture gameplay activity. Future downloaded/local records remain independent of room expiry.

## Browser recovery and verification

Room credentials remain in tab session storage. Guest access credentials are browser-scoped in local storage; queue tickets, queue mode and the admission operation key are tab-local. Reload or a lost admission response retries the same operation, recovering the same seat. Successful room entry retires its key; leave → create/rejoin uses a fresh key. Storage failure is reported. Private invitation links contain only code/display hints; public display tabs receive a separate viewing credential in their own session storage.

A missing server ticket retires the stale browser ticket and checks the guest's current claim. An in-flight queue entry is allowed to complete before classifying its ticket as missing. Check previous session and explicit Leave previous laboratory/Cancel previous queue controls recover issued guest identities even after a room credential is lost. Recovery preserves the identity, uses owner authentication and the observed claim nonce, and revokes the matching seat before conditionally releasing its claim. It never resets the guest or releases a newer claim automatically. Existing aliases intentionally survive reload.

`npm run check` covers configuration, both TypeScript projects and deterministic/component regressions. `npm run test:rooms` builds/dry-runs and tests independent private-room clients, real alarms, SQLite, eviction and restart. `npm run test:matchmaking` also uses independent network queue/room clients with isolated SQLite storage, real ready/fallback timers, cross-pool fences, persisted journal recovery, replacements and restart. Historical orchestration fixtures seed legacy battle/regroup/recovery boundaries. New combat tests exercise the actual producer, results and three-round progression with real independent clients; later fixture deadlines are advanced only in isolated SQLite.

No runtime test publishes a Worker. The user has separately confirmed deployed multi-device verification for steps 1–3. This session has not repeated it; cross-region latency, delayed/lost packets and free-tier load/quota measurements remain separate validation. Account access and health alone cannot establish these results.

## Authoritative DNA and release

`src/server/catalogue/dna.ts` contains all 30 executable definitions and explicit logical targets versus produced render attachments; `catalogue/mechanics.ts` pins baseline stats, signed effect and ability caps, units and future-producer constraints. `dna-mechanics.ts` owns dealing, injection, switch eligibility, composition and freezing. These modules are never imported into the client.

New attempts pin rules 0.3.0/catalogue 0.2.0 (existing schema-4 attempts retain rules 0.2.0), has an opaque UUID and independent public visual entropy, and starts with a fresh baseline blob. At the existing eight-second briefing boundary, lock N to the eligible connected cohort (2–8), initialize four private specimens, six precomputed replacement packets, six doses and participation counters. Each packet contains a weighted primary and safe fallback; the actual remaining tray determines which is used, ensuring it cannot become entirely liabilities. Server entropy is independent of the public composition seed. Reconnect/eviction/restart never deals again.

Private specimens contain opaque IDs, accessions and stable non-spoiling clue keys/descriptions. Only the owning player receives their four specimens, dose budget and cooldown. During experiment/release, public projections include current anatomy, post-injection names/attribution, active/partial/replaced history and coarse readings; they exclude hidden DNA IDs before injection, draw order, stats, abilities, seeds and tokens. Displays have no controller projection. Original code-authored SVG clues and provenance are separate from the unchanged raster-art ledger.

Injection and pull-switch intentions require the current attempt UUID under protocol 5. Both socket protocol names derive from the shared version constant. Earlier-protocol handshakes/messages reject with reload guidance, preserving credentials/leases. Controller projections include revision and attempt context. Serialized actions look up matching SQL receipts before mechanics eligibility, validate on a cloned candidate, and atomically commit state, receipt and alarm before acknowledgment. Duplicate accepted requests cannot consume another dose/draw; changed reuse conflicts; rejected mechanics retries retain their result. Valid rate-limited requests return their action ID so controllers resolve pending feedback.

Accepted injection consumes one dose, replaces only the selected specimen, starts a six-second cooldown, records ordering/attribution and changes the shared creature immediately. New actions reject at the exact 75-second deadline. Contributions use 2/N with N fixed at start. Different DNA replaces a logical owner; identical DNA stacks using the approved diminishing curve and cap. Paired limbs split ownership/potency; replacing the right removes only that half. Recompute effects from baseline plus surviving parts, then clamp, so replaced benefits and penalties cannot leave residual mechanics. Cosmetics consume a dose normally and add no numerical bonus. The complete calibration is in STEP-5-PLAN.md; it is not validated combat balance.

Unleash requires one accepted injection and completed cooldown. It irrevocably finishes the player and forfeits unused doses. Spending six doses does not pull it automatically. Voluntary switch, grace expiry, departure and deadline completion have distinct reasons. Unanimity or deadline invokes one idempotent release function, storing the creature, exact hidden stats, abilities, surviving attribution, versions, constraints and history once. Release lasts exactly five authoritative seconds; injections remain locked. This frozen server-only record is the combat producer input. Its release portrait stays unchanged while battle detachment operates on a separate copy. Card export is still outside this milestone.

The client persists the exact pending injection/switch in tab storage scoped to room/seat/attempt. After reconnect/reload and synchronization it retries the same ID/payload. Acknowledgment cannot unlock controls before the corresponding private revision arrives. Changed attempts retire stale pending intentions while retaining identity. Selection is local; budget and creature update only from accepted state. Waiting/recovery/finished/disconnected controls remain locked; every device gets the same latest public anatomy.

The chamber retains one renderer across mutations, updates sprites by stable part IDs, ignores superseded image-load generations and coalesces one short accent toward the latest anatomy. Static fallback uses that same new composition while loading or when graphics fail. Reduced motion makes direct updates; resizing/art retry never owns transport. Body/skin overlaps and limb mirroring use the produced metadata with bounded scale/style descriptors. A shared body-relative projection resolves named sockets, real attachment pivots, anatomical depth and fitting around stable roots for both Pixi and static DOM. Metadata also supplies authored height proportions, root-preserving rotation, per-pose mirroring and presentation opacity. Raised paws reflect their upward-rotated pose; foreground legs and mantle layering follow the definitive user sheet. Shared sRGB color matrices affect presentation only and preserve alpha in Pixi and SVG fallback; filters are disposed with sprites. Full-body replacement artwork includes its rounded blank head within a single texture, without adding any replaced blob part. The 9 October high-resolution calibration uses deterministic SVG assemblies of the original body/modules; a canonical anatomical frame remains independent of their taller texture extents. Independent right-side pose metadata preserves source asymmetry. Baseline face proportions are retained; only reinforcement is capped. Rotated transparent corners fit the glass drawing bounds rather than shrinking raised paws to the nominal frame. See [CREATURE-COMPOSITION-REVIEW.md](CREATURE-COMPOSITION-REVIEW.md) for body profiles, calibrated metadata, artwork provenance and the development-only authoritative gallery. Captions remain in a keyboard-scrollable mutation log; approximate readings do not reveal hidden numerical outcomes.

## Combat rendering and evidence

`src/server/combat.ts` and `catalogue/combat.ts` own seeded attacks, status durations, control immunity/budget, finite detached hazards, outcome and contribution evidence. All values and initial rival tables are versioned; existing DNA values/scaling are unchanged. See STEP-6-PLAN.md for exact calibration and attribution rules. Session score is the sum of actual completed outcomes. The six commendations use qualifying observed evidence, share ties, exclude baseline/overwritten active mechanics and never claim a player caused victory. Late seats receive only their own subsequent credit.

`BattleStage.tsx` uses the shared anatomical projection/color matrices in a ground-aligned SVG stage, real optimized rival sprites, health meters, condition badges, bounded recent captions and a keyboard-scrollable chronological record. `battle-playback.ts` seeks directly to a server timestamp, including after reload or skipped frames. No client selects mutations or computes game outcomes. The chamber remains mounted and paused during battle; resource ownership and sockets retain their existing lifecycle. Static/reduced motion uses the same authoritative anatomy, health and text. Art failures expose a retry without blocking controls.

`/combat-gallery` is Vite-only and uses six deterministic public timelines produced by `scripts/prepare-combat-fixtures.mjs`; it is eliminated from production bundles and has no Worker route. Rival source/provenance remains outside public assets; only same-origin WebP sprites and a minimal render index ship. No runtime generation or new hosting requirement is introduced.
